# ログ解析システム 要件定義書

## 1. プロジェクト概要

### 1.1 プロジェクト名
**DuckDB WASM ログ解析システム**

### 1.2 目的
自然言語入力により、アプリケーションログを解析し、インタラクティブなグラフで可視化するWebアプリケーションを構築する。

### 1.3 対象ユーザー
社内開発チーム（複数チーム）

### 1.4 期待される効果
- ログ解析の民主化（SQLスキル不要）
- 障害調査時間の短縮
- データドリブンな意思決定の促進
- チーム間のデータ分離とセキュリティ確保

---

## 2. 機能要件

### 2.1 認証・認可

#### 2.1.1 ユーザー認証
- **必須機能**
  - メールアドレスとパスワードによるログイン
  - セッション管理
  - ログアウト機能
  - パスワードリセット
- **サインアップ方式**
  - 管理者がCognitoコンソールまたはCLIで事前にユーザー作成
  - 初回ログイン時に仮パスワードから本パスワードへ変更を強制
  - チーム割り当ては管理者が実施（Cognitoグループへの追加）
  - セルフサインアップは無効化（社内限定のため）

#### 2.1.2 チームベースアクセス制御
- **必須機能**
  - ユーザーは1つ以上のチームに所属
  - チームに紐づくログのみ閲覧可能
  - 管理者ロールは全チームのログにアクセス可能
  - **セキュリティ対策**:
    - S3への直接アクセス禁止（IAMポリシーで制限）
    - バックエンドでSigned URL（15分有効）を生成
    - バックエンドでチーム権限を検証してからアクセス許可
    - SQLにteam_idフィルタを強制適用
- **チーム例**
  - `team-alpha`: チームAlphaのログのみ
  - `team-beta`: チームBetaのログのみ
  - `team-admin`: 全チームのログ

### 2.2 ログデータ管理

#### 2.2.1 ログの取り込み
- **データソース**: AWS Kinesis Firehose
- **保存先**: Amazon S3
- **フォーマット**: JSONL（改行区切りJSON）
- **圧縮形式**: GZIP
- **パーティション戦略**: team_id/年/月/日/時間別
  ```
  s3://bucket/logs/team_id=team-alpha/year=2024/month=01/day=15/hour=10/
  ```
- **パーティション説明**: team_idを最上位に配置することで、チーム別アクセス制御を強化

#### 2.2.2 ログスキーマ
| フィールド名 | 型 | 必須 | 説明 |
|------------|-----|------|------|
| timestamp | TIMESTAMP | ✓ | ログ発生時刻（ISO 8601） |
| level | VARCHAR | ✓ | ログレベル（INFO/WARN/ERROR/DEBUG） |
| service | VARCHAR | ✓ | サービス名/マイクロサービス識別子 |
| message | TEXT | ✓ | ログメッセージ |
| team_id | VARCHAR | ✓ | チーム識別子（アクセス制御用） |
| user_id | VARCHAR | - | ユーザー識別子 |
| duration_ms | INTEGER | - | 処理時間（ミリ秒） |
| status_code | INTEGER | - | HTTPステータスコード |
| endpoint | VARCHAR | - | APIエンドポイント |
| method | VARCHAR | - | HTTPメソッド（GET/POST等） |
| error | TEXT | - | エラーメッセージ詳細 |
| trace_id | VARCHAR | - | 分散トレーシングID |
| ip_address | VARCHAR | - | 送信元IPアドレス |
| request_id | VARCHAR | - | リクエスト識別子 |

#### 2.2.3 データ量
- **想定サイズ**: 数GB/日
- **保持期間**: 90日間（要調整）
- **1回のクエリ対象**: 最大500MB（圧縮後）
- **ブラウザメモリ考慮**: 500MB GZIP圧縮ファイルは解凍後1.5-2.5GB程度を想定
- **データサイズ超過時**: 警告表示し、日付範囲の縮小を促す

### 2.3 ログ検索・解析

#### 2.3.1 日付範囲選択
- **必須機能**
  - カレンダーUIによる開始日・終了日の選択
  - プリセット選択
    - 過去1時間
    - 過去24時間
    - 過去7日間
    - 過去30日間
    - カスタム範囲
- **制約**
  - 最大選択範囲: 30日間
  - 最大データサイズ: 500MB（圧縮後）
  - データサイズ警告閾値: 400MB（推定データサイズが400MB超過時に警告表示）

#### 2.3.2 自然言語クエリ
- **シンプルなクエリ例**
  - "過去24時間のエラーログを表示"
  - "最も遅いエンドポイントは？"
  - "ユーザーuser123のアクティビティを表示"
  - "今日のログレベル別の件数を表示"

- **複雑なクエリ例**
  - "先週と比較して今週のエラー率の変化を分析"
  - "レスポンスタイムが500ms以上のリクエストで、エラーになったものの相関関係"
  - "異常なアクセスパターンを検出"
  - "時間帯別のエンドポイント別リクエスト数をヒートマップで表示"

- **会話形式のクエリ**
  - 前の質問の結果を踏まえた追加質問
  - 例:
    ```
    ユーザー: "過去24時間のエラーログを表示"
    システム: [結果表示]
    ユーザー: "そのエラーの詳細を表示"
    システム: [詳細表示]
    ユーザー: "それをグラフにして"
    システム: [グラフ表示]
    ```

#### 2.3.3 SQL生成
- **AI処理**
  - 自然言語をDuckDB SQLに変換
  - 会話履歴を考慮したコンテキスト理解
  - チームIDフィルタの自動適用（セキュリティ）
  - 日付範囲フィルタの自動適用

- **SQL検証（バックエンドで実施）**
  - 基本的な構文チェック
  - team_idフィルタの強制確認（WHERE句に必須）
  - 危険なクエリの検出（DROP、DELETE、UPDATE、INSERT等）
  - SELECT文のみ許可
  - 検証失敗時は具体的なエラーメッセージを返却

- **エラーハンドリング**
  - AI生成SQLが不正な場合、ユーザーに修正提案を表示
  - 実行時エラー（構文エラー、タイムアウト等）の詳細表示
  - ユーザーが質問を言い換えて再試行できるUI

#### 2.3.4 クエリ実行
- **実行環境**: ブラウザ内（DuckDB WASM）
- **処理フロー**
  1. バックエンドAPI（Next.js Route Handler）にクエリリクエスト送信
  2. バックエンドでユーザー認証・チーム権限を検証
  3. 該当期間のS3ログファイルパスを取得
  4. チームIDでフィルタリングしたファイル一覧を返却
  5. バックエンドで各ファイルのS3 Signed URL（有効期限15分）を生成
  6. ブラウザでSigned URLからファイルをストリーミング読み込み
  7. GZIP自動解凍
  8. DuckDB WASMでSQLクエリ実行
  9. 結果をJSON形式で取得

- **パフォーマンス要件**
  - レスポンス時間（P95）: 15秒以内
  - レスポンス時間（P99）: 30秒以内
  - タイムアウト: 60秒
  - メモリ使用量: ブラウザ制限内（2-4GB）
  - エラー時のフォールバック: タイムアウト時は範囲縮小を提案

### 2.4 データ可視化

#### 2.4.1 グラフタイプ

**時系列グラフ（折れ線グラフ）**
- **用途**: ログレベル別の推移、エラー数の時系列変化
- **軸**
  - X軸: 時間（分/時間/日単位）
  - Y軸: 件数
- **機能**
  - 複数系列の表示（INFO/WARN/ERROR）
  - ズーム・パン
  - ツールチップ表示

**円グラフ**
- **用途**: ログレベルの割合、サービス別の分布
- **機能**
  - パーセンテージ表示
  - 凡例表示
  - セグメントのハイライト

**棒グラフ**
- **用途**: エンドポイント別リクエスト数、レスポンスタイム比較
- **軸**
  - X軸: カテゴリ（エンドポイント、サービス等）
  - Y軸: 数値（件数、平均時間等）
- **機能**
  - 横棒・縦棒の切り替え
  - ソート機能（昇順・降順）

**ヒートマップ**
- **用途**: 時間帯別・曜日別のアクセスパターン
- **軸**
  - X軸: 時間帯（0-23時）
  - Y軸: 曜日（日-土）
- **色**: リクエスト数の多寡を色の濃淡で表現
- **機能**
  - カラースケールの調整
  - セルのツールチップ

#### 2.4.2 ドリルダウン機能
- **必須機能**
  - グラフの特定ポイントをクリック
  - クリックされたデータの詳細を自動クエリ
  - 詳細ビューの表示（テーブルまたは別グラフ）
  - パンくずリストによる階層表示

- **例**
  ```
  1. 時系列グラフで「2024-01-15 10:00」のエラー数をクリック
  2. その時間帯のエラーログ一覧を表示
  3. 特定のエラーをクリック
  4. そのエラーのスタックトレースや関連ログを表示
  ```

#### 2.4.3 結果テーブル
- **必須機能**
  - クエリ結果の表形式表示
  - カラムのソート
  - ページネーション（50件/100件/500件）
  - CSVエクスポート
- **オプション機能**
  - カラムの表示/非表示切り替え
  - フィルタリング

### 2.5 会話履歴管理

#### 2.5.1 履歴の保存
- **保存内容**
  - ユーザーの質問（自然言語）
  - 生成されたSQL
  - クエリ結果のサマリー
  - タイムスタンプ
  - 選択されていた日付範囲

#### 2.5.2 履歴の表示
- **UI要件**
  - サイドバーまたはドロワーに履歴一覧
  - 時系列順に表示
  - 履歴項目をクリックで結果を再表示

#### 2.5.3 コンテキスト維持
- **必須機能**
  - 前の質問の結果を参照する質問に対応
  - 代名詞（「それ」「その」等）の解決
  - 会話の流れを考慮したSQL生成

### 4.2 システムアーキテクチャ

#### 4.2.1 アーキテクチャパターン
**ハイブリッドアーキテクチャ**
- フロントエンド: クライアントサイド処理（DuckDB WASM）
- バックエンド: サーバーサイド処理（AI、認証）
- データ: S3（静的ファイル）

#### 4.2.2 データフロー
```
[ユーザー入力（自然言語）]
    ↓
[Next.js Route Handler] → [Cognito検証] → [チーム権限取得]
    ↓
[Bedrock API] → [SQL生成]
    ↓
[SQL検証（team_idフィルタ強制確認）]
    ↓（検証OK）
[S3ファイル一覧取得] → [team_idパスでフィルタリング]
    ↓（例: s3://bucket/logs/team_id=team-alpha/year=2024/...）
[S3 Signed URL生成（有効期限30分）]
    ↓（Signed URLを返却）
[ブラウザ（DuckDB WASM）]
    ↓
[CloudFront経由でSigned URLからファイルストリーミング読み込み]
    ↓
[GZIP解凍 + SQLクエリ実行]
    ↓
[結果をJSON取得]
    ↓
[Recharts] → [グラフ描画]
```

#### 4.2.3 認証フロー

```
[ユーザー] → [Cognito Hosted UI]
    ↓

    ↓

[トークン検証 + グループ情報取得]

```

### 4.3 セキュリティアーキテクチャ

#### 4.3.1 多層防御戦略
```
[レイヤー1: 認証]
- Cognito による本人確認
- セッション管理（24時間有効）

[レイヤー2: 認可]
- Cognitoグループによるチーム権限管理
- バックエンドでのチーム権限検証

[レイヤー3: データアクセス制御]
- S3へは直接アクセス不可（IAMポリシーで制限）
- Signed URL（30分有効）経由のみアクセス許可
- S3パーティション構造でteam_id分離（s3://bucket/logs/team_id=xxx/）
- バックエンドでteam_idパスのみアクセス許可

[レイヤー4: SQL検証]
- バックエンドでteam_idフィルタ強制確認
- SELECT文以外の禁止
- 危険なクエリの検出

[レイヤー5: 監査ログ]
- CloudWatch Logsにアクセスログ記録
- ユーザー、クエリ内容、結果サマリーを記録
```

#### 4.3.2 Signed URL生成仕様
- **有効期限**: 30分（大容量ファイルのダウンロード時間を考慮）
- **生成タイミング**: クエリ実行時にバックエンドで生成
- **権限検証**: ユーザーのチームIDとファイルパスのteam_idを照合
- **実装**: AWS SDK for JavaScript v3の `getSignedUrl()`使用
- **有効期限切れ対応**: フロントエンドで検知し、自動的にURL再生成をリクエスト

### 4.4 データモデル

#### 4.4.1 S3パーティション構造
```
s3://log-analyzer-bucket/
└── logs/
    └── team_id=team-alpha/
        └── year=2024/
            └── month=01/
                └── day=15/
                    └── hour=10/
                        ├── app-logs-2024-01-15-10-00-001.jsonl.gz
                        ├── app-logs-2024-01-15-10-05-002.jsonl.gz
                        └── app-logs-2024-01-15-10-10-003.jsonl.gz
    └── team_id=team-beta/
        └── year=2024/
            └── month=01/
                └── ...
```

**パーティション設計の利点**:
- team_idを最上位パーティションに配置することで、チーム別のアクセス制御が容易
- S3パス自体でチーム分離が明確
- バックエンドでのファイル一覧取得時に、team_idパスでフィルタリング可能
- Firehose Dynamic Partitioningでteam_id、year、month、day、hourを自動振り分け

#### 4.4.2 Firehose設定
| 設定項目 | 値 | 理由 |
|---------|-----|------|
| バッファサイズ | 128 MB | 圧縮効率とレイテンシのバランス |
| バッファ間隔 | 300秒（5分） | リアルタイム性とコスト |
| 圧縮形式 | GZIP | DuckDB WASM対応、高圧縮率 |
| Dynamic Partitioning | 有効 | 日付別パーティション自動作成 |
| エラーログ出力 | S3別バケット | トラブルシューティング |

#### 4.4.3 DuckDBテーブルスキーマ
```sql
CREATE TABLE logs (
  timestamp TIMESTAMP NOT NULL,
  level VARCHAR NOT NULL,
  service VARCHAR NOT NULL,
  message TEXT NOT NULL,
  team_id VARCHAR NOT NULL,
  user_id VARCHAR,
  duration_ms INTEGER,
  status_code INTEGER,
  endpoint VARCHAR,
  method VARCHAR,
  error TEXT,
  trace_id VARCHAR,
  ip_address VARCHAR,
  request_id VARCHAR
);

-- インデックス（パフォーマンス最適化）
CREATE INDEX idx_timestamp ON logs(timestamp);
CREATE INDEX idx_level ON logs(level);
CREATE INDEX idx_team_id ON logs(team_id);
CREATE INDEX idx_service ON logs(service);
```

### 4.5 AI処理仕様

#### 4.5.1 Bedrock設定
| 設定項目 | 値 | 理由 |
|---------|-----|------|
| モデル | Claude 3.5 Sonnet | 最新、高精度、コスト効率 |
| Temperature | 0.1 | SQL生成の確実性重視 |
| Max Tokens | 4096 | 複雑なクエリ対応 |
| リージョン | us-east-1 | Bedrock利用可能リージョン |

#### 4.5.2 プロンプト構造
```
<system>
- ロール定義: DuckDB SQL専門家
- スキーマ情報
- ルール（team_idフィルタ必須、日付範囲制限等）

<user>

```

#### 4.5.3 SQL検証ルール（バックエンドで実施）
- `SELECT`文のみ許可
- **禁止コマンド（完全一致・大文字小文字区別なし）**:
  - DML: `DROP`, `DELETE`, `UPDATE`, `INSERT`, `TRUNCATE`, `MERGE`
  - DDL: `CREATE`, `ALTER`, `RENAME`
  - DuckDB特有: `COPY`, `ATTACH`, `DETACH`, `INSTALL`, `LOAD`, `EXPORT`, `IMPORT`
  - システム系: `PRAGMA`, `SET`, `CALL`
- `team_id`フィルタの存在確認（WHERE句に必須）
  - 管理者以外は必ず `WHERE team_id = 'team_xxx'` を含む
  - 管理者は全チーム参照可能
- 日付範囲フィルタの存在確認
- セミコロンで終了
- コメントの除去
- **複文の禁止**: セミコロンが2つ以上含まれる場合はエラー
- 検証失敗時のエラーメッセージ例:
  - "team_idフィルタが含まれていません。セキュリティ上必須です。"
  - "SELECT文以外は実行できません。"
  - "禁止されたコマンド '{コマンド名}' が検出されました。"

## 5. 制約事項

### 5.1 技術的制約
- **ブラウザメモリ制限**: 2-4GB（ブラウザ依存）
- **1回のクエリデータ量**: 最大500MB（圧縮後、解凍後は1.5-2.5GB程度）
- **日付範囲選択**: 最大30日間
- **同時実行クエリ**: 1ユーザーあたり1クエリ
- **ファイル形式**: JSONL + GZIP のみ対応

### 5.2 ビジネス制約
- **対象**: 社内ユーザーのみ
- **サポートブラウザ**: Chrome、Edge、Safari最新版
- **デバイス**: デスクトップ、タブレット（スマートフォン非対応）
- **言語**: 日本語のみ
- **タイムゾーン**: JST（日本標準時）

### 5.3 コスト制約
- **月間予算**: 約$200-300（詳細試算に基づく）
- **主要コスト要素**（想定: 10ユーザー、1日あたり5GB、月間150GB、1ユーザーあたり1日5クエリ × 平均500MB読み込み）:
  - **Bedrock API**: $30-50/月
    - Claude 3.5 Sonnet: $0.003/1K input tokens、$0.015/1K output tokens
    - 想定: 1クエリあたり平均3K tokens、100クエリ/日
  - **S3ストレージ**: $4/月
    - $0.023/GB/月 × 150GB（90日間保持、1日5GB）
  - **S3 GETリクエスト**: $5/月
    - $0.0004/1K requests × 約12M requests/月
  - **データ転送（S3→CloudFront）**: $10-15/月
    - $0.020/GB × 750GB/月（10ユーザー × 5クエリ/日 × 500MB × 30日）
  - **CloudFront→インターネット**: $60-75/月
    - $0.085/GB × 750GB/月（CloudFront経由、キャッシュ効率30%想定）
  - **Amplify Hosting**: $10/月
    - ビルド時間、SSRリクエスト、ホスティング
  - **CloudWatch Logs**: $5/月
- **コスト最適化策**（**必須**: CloudFrontは必須項目として実装）:
  - **CloudFront経由でのキャッシュ活用**（データ転送コストを40-50%削減）
  - S3 Intelligent-Tiering適用（アクセス頻度に応じた自動階層化）
  - ログ保持期間を90日→60日に短縮検討
  - 予算超過アラート設定（月間$300超過時）
  - 頻繁にアクセスされる日付範囲のデータをCloudFrontでキャッシュ（TTL: 1時間）
